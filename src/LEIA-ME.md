# Código-fonte do site

Para continuar o trabalho num novo ambiente, montar a pasta de trabalho (aqui, /home/claude, com o clone do repositório em /home/claude/precons-commander):

    cp -r src/dados/* /home/claude/ && cp src/build.py src/template.html src/normalizar.py src/publicar.sh /home/claude/ && cp -r src/tools /home/claude/
    mkdir -p /home/claude/site && cp -r index.html nomes_pt.json sw.js README.md manifest.json icon.svg icon-*.png icons /home/claude/site/

Os scripts não têm pasta fixa: usam a pasta onde estão (`build.py`, `normalizar.py`, `publicar.sh`) ou a pasta acima de `tools/` (`tools/*.py`). Para usar outra pasta, definir `PRECONS_RAIZ` (scripts Python) ou `PRECONS_SITE` e `PRECONS_REPO` (`publicar.sh`).

- `tools/raspar.py SET slug pasta stem` baixa https://mtg.wtf/deck/SET/slug e grava raw/pasta/stem.txt (comandantes, `--`, demais cartas; ignora Display Commander e tokens; confere somas das seções).
- `normalizar.py raw/pasta/stem.txt` grava pasta/stem.txt no formato final (comandante(s), linha em branco, resto em ordem alfabética) e mostra o total de cartas, duplicatas e conflitos de número.
- `tools/validar.py` confere todas as listas sem internet: formato, 100 cartas, duplicatas (exceto as impressas assim no produto, em `EXCECOES`), conflitos de número, ordem alfabética (aviso; com `--estrito`, erro) e se todo deck do build.py tem arquivo e vice-versa. Com `--site PASTA`, gera o site de novo e confere se sai idêntico ao index.html e nomes_pt.json publicados. Roda sozinho no GitHub Actions a cada push (`.github/workflows/validar.yml`, com `--raiz src --site .`); rodar antes de publicar: `python3 tools/validar.py --site site`.
- `tools/auditar.py` reconfere todos os decks do build.py contra o mtg.wtf (manual; precisa de internet).
- `build.py` (lista C de coleções, ANOS e ícones) gera precons_offline.html a partir de template.html; copiar para site/index.html; atualizar a lista de ícones e a versão em site/sw.js; publicar com `publicar.sh "mensagem"`. O rodapé do commit é opcional: `COAUTOR="Claude Opus 5.5 <noreply@anthropic.com>" SESSAO="link da sessão" ./publicar.sh "mensagem"`.
- `tools/atributos.py` gera `cartas.csv` (uma linha por carta: cores, identidade de cor, custo, valor de mana, tipos, nome em português) e `impressoes.csv` (uma linha por edição+número: raridade) a partir das listas dos decks e do Scryfall. Precisa de acesso a api.scryfall.com e data.scryfall.io; roda em cerca de 1 minuto (`python3 tools/atributos.py`, cache em /tmp/atributos-cache). Rodar de novo sempre que entrar deck novo; ele para com erro se alguma carta de alguma lista não for achada no Scryfall. O `build.py` lê os dois CSV (copiados de src/dados para a pasta de trabalho) e gera `nomes_pt.json` (nome da carta na lista -> nome em português, 4.998 nomes, 79 KB gzip), que o site carrega ao tocar no filtro para buscar e sugerir em português. Também embute em cada deck o campo `ci` (identidade de cor do(s) comandante(s), para o filtro "Por cor") e para com erro se algum comandante não estiver em `impressoes.csv`. Depois de rodar `tools/atributos.py`, rodar `python3 build.py`, copiar `precons_offline.html` para `site/index.html` e `nomes_pt.json` para `site/` (o `publicar.sh` leva ao repositório).
- `tools/arquetipos.py` classifica cada deck em até 2 arquétipos (tribal, tokens, counters, spellslinger, graveyard, artifacts, enchantments, lifegain, sacrifice, voltron, blink, lands; sem nenhum chegar ao limite, fica o de maior score, marcado fraco=1) e grava `decks.csv` (uma linha por deck: id, nome, comandante, coleção, arq1, arq2, tribo e as contagens n_<arquétipo> que justificam). Regra: contagem de cartas distintas (sem terrenos) que casam o texto de regras do Scryfall, dividida por um limite fixo (`LIMITES` no script); entram os 2 maiores scores >= 1, o 2º só se for >= 60% do 1º. Precisa de data.scryfall.io (usa o cache de `atributos.py`). Rodar `python3 tools/arquetipos.py --ver` sempre que entrar deck novo ou mudar a regra; o `validar.py` confere que a tabela cobre todos os decks. `decks.csv` fica em src/dados/.
- Ao mudar build.py, template.html, normalizar.py, publicar.sh, tools/ ou alguma lista, copiar também para src/ (e as listas para src/dados/); se esquecer, o validador do GitHub Actions acusa que o site publicado difere do código-fonte.
